# Що ми робимо

**Attendance Planner Agent** — агент, який дивиться на розклад університету і
каже студенту: **у які дні приходити на кампус і на яку групу йти на кожен
предмет**, щоб закрити максимум обовʼязкових занять за мінімум днів і не
перетнутися з особистим календарем.

## Навіщо

В універі можна ходити не тільки зі своєю групою: та сама пара з тієї самої
теми читається кілька разів на тиждень для різних груп. Тобто розклад — це не
фіксований набір, а простір варіантів. Вручну цей простір не перебереш: 4
предмети × 3 групи × календар із роботою й іншими справами дають десятки
комбінацій, і людина обирає навмання.

Плюс розклад редагують посеред семестру. План, складений у понеділок, у середу
може бути вже неправильним — і про це ніхто не повідомляє.

Агент вирішує обидві задачі: перебирає варіанти за реальними обмеженнями і
сам помічає, коли розклад змінився і план треба перерахувати.

## Як це працює

```
публічна сторінка розкладу
        │  Playwright MCP (браузер, окремий процес)
        ▼
   сирий HTML ──► ingest_timetable_snapshot ──► версіонований снапшот
                                                      │
                        detect_timetable_changes ◄─────┘
                                │
                    змін немає ──┴── є зміни
                        │              │
                        │      detect_schedule_conflicts   (проти .ics календаря)
                        │              │
                        │      optimize_attendance_plan    (мінімум днів на кампусі)
                        │              │
                        │      compare_attendance_plans    (чи взагалі досяжна твоя вимога)
                        ▼              ▼
                          фінальна відповідь студенту
```

Приклад того, що агент видає на виході:

> Приходь у вівторок і четвер — два дні замість чотирьох.
> ECON301 — лекція з групою BE-3-2 у вівторок 09:00 (не своя група, тема та сама).
> STAT210 — семінар зі своєю групою у четвер 10:40.
> MGMT150 — з групою BE-3-3 у четвер 12:20.
> FIN220 — пропускаєш: єдиний варіант у середу перетинається зі зміною на роботі.
> Покриття 75%, твоя вимога «не більше 3 днів» виконана.

## Чому саме так, з погляду завдання

Завдання вимагає два MCP-підключення в одному звʼязному агентному флоу.

**Part A — Playwright MCP** (з дозволеного списку). Розклад університет
публікує лише як сторінку, публічного API немає. Це єдиний із трьох дозволених
серверів, який може дістати першоджерело. Він же дає чесний сценарій збою:
сервер не запущено, сторінка недоступна, селектор зник.

**Part B — власний MCP-сервер `schedule-mcp`**, окремий процес, пʼять
інструментів:

| Інструмент | Що робить | Не пошук? |
|---|---|---|
| `ingest_timetable_snapshot` | парсить, нормалізує, валідує, версіонує розклад | так |
| `detect_timetable_changes` | diff двох версій розкладу + вплив на чинний план | так |
| `detect_schedule_conflicts` | типізовані конфлікти з календарем і між парами | так |
| `optimize_attendance_plan` | оптимізація під мінімум днів із крос-груповою заміною | так |
| `compare_attendance_plans` | перевіряє заявлену вимогу студента проти чисел | так |

Головний принцип поділу: **модель вирішує, що спитати; сервер вирішує, що є
правдою.** Усе, що має бути детермінованим, перевірюваним і стійким до
бажання моделі видати гарну відповідь, живе в сервері. Оптимізацію не можна
довіряти промпту — LLM вигадає правдоподібний, але не оптимальний і
невідтворюваний варіант.

## Межі проєкту

Робимо тільки планування відвідування. Moodle-дедлайни й нотатки з Telegram —
свідомо поза обсягом: завдання оцінює звʼязність одного домену, а не кількість
фіч, і Telegram не проходить вимогу «public API without authentication».

Дані: локальний детермінований датасет + записані фікстури сторінки.
Особистий календар — експортований `.ics` файл, до акаунта агент не лізе.
Навігація тільки по публічній сторінці, без логінів і без форм.

## Як розділена робота

Проєкт веде одна людина з кількох машин: на кожному ноуті своя сесія Claude
Code, але GitHub-акаунт один. Робота поділена на треки, які не перетинаються по
каталогах, тому дві сесії можуть іти паралельно й не наступати одна одній на
ноги.

| Трек | Каталог | Відповідальність |
|---|---|---|
| **A** | `mcp_servers/` | власний MCP-сервер: інструменти, схеми, помилки, тести |
| **B** | `agent/` | агент на LangGraph, обидва MCP-підключення, обробка збоїв |
| **C** | `docs/`, `fixtures/` | контракти інструментів, rationale, сценарій захисту, фікстури |
| **D** | — | інтеграція і репетиція захисту, наприкінці |

Синхронізація йде виключно через GitHub Issues: сесія клеймить тікет
коментарем `/take <імʼя сесії>`, бот позначає його `status:in-progress` і
відмовляє всім іншим. Коли PR мерджиться, бот сам розблоковує залежні тікети —
це і є сигнал наступній сесії.

## Як підняти ще одну машину

1. Постав інструменти й авторизуй **той самий** GitHub-акаунт:
   `gh auth login`, потім `gh auth status` має показати `dvasylchuk`.
2. Задай імʼя сесії — воно йде в claim-коментарі й назви гілок:
   `[Environment]::SetEnvironmentVariable("AGENT_NAME", "laptop-b", "User")`
3. Постав оточення:

   ```powershell
   git clone https://github.com/dvasylchuk/kse-attendance-agent.git
   cd kse-attendance-agent
   python -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   copy .env.example .env
   python scripts/verify_mcp.py     # має вивести 5 інструментів
   ```

4. Візьми перший вільний тікет треку цієї машини:

   ```powershell
   bash scripts/next_ticket.sh track:B-agent
   gh issue comment 12 --body "/take $env:AGENT_NAME"
   ```

5. Далі за `CLAUDE.md` — там повний протокол для сесії Claude Code.
