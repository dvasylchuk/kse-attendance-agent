# План роботи

## Що саме будуємо

Агент відповідає на одне питання: **у які дні і з якою групою ходити на пари,
щоб закрити максимум обовʼязкових занять за мінімум днів на кампусі й не
перетнутися з особистим календарем.**

Це навмисно вужче за початкову ідею (розклад + Moodle + Telegram). Завдання
оцінює не кількість фіч, а якість двох MCP-підключень і звʼязність одного
робочого флоу. Три різні джерела дали б три поверхові інтеграції; одна
предметна область дає пʼять змістовних інструментів і замкнений цикл
прийняття рішень. Moodle і Telegram лишаються в «Можливі розширення» —
згадати на захисті як напрямок, не реалізовувати.

## Чому саме ця тема проходить за вимогами

| Вимога завдання | Як закрито |
|---|---|
| Domain-specific data agent, не одноразовий lookup | багатокроковий флоу: скрейп → снапшот → diff → конфлікти → оптимізація → порівняння → звіт |
| Результат інструмента впливає на наступний крок | `detect_timetable_changes.replan_required` вирішує, чи запускати оптимізацію взагалі; `INFEASIBLE` змушує агента послабити обмеження і повторити |
| Existing MCP з дозволеного списку | Playwright MCP — публічна сторінка розкладу, публічного API немає |
| Custom MCP, окремий процес, ≥3 змістовні інструменти | 5 інструментів, з них 4 не є пошуком/ретрівалом |
| Primary data-source tool | `ingest_timetable_snapshot` — єдина точка входу сирих даних |
| Public API без авторизації **або** локальний датасет | локальний датасет `data/` + записані фікстури; мережевий доступ лише через Playwright |
| Помилки відрізняються від порожнього результату | конверт `{ok, data, warnings}` / `{ok:false, error{code,message,details,retryable}}` |
| Реалістичний збій existing-сервера | сервер не запущено / недоступна сторінка / селектор не зʼявився → деградація на фікстуру з поясненням |

Тут і нижче "селектор" описано як для `<table class="schedule">` (синтетичні
фікстури `fixtures/playwright/schedule_page_v*.html`). Реальна публічна
сторінка (`schedule.kse.ua`, підтверджено в тікеті B0) має іншу структуру —
div-грід, не таблицю — і парсер підхоплює обидва варіанти автоматично. Деталі
й наслідки для B2/C3/D2: [`docs/00-execution-plan.md`](00-execution-plan.md).

## Розподіл на треки

Три треки йдуть паралельно, бо не перетинаються по файлах.

| Трек | Людина | Каталог | Тікети |
|---|---|---|---|
| **A — custom MCP server** | Dev A | `mcp_servers/` | A3, A4, A5, A6, A7 (A1, A2 вже зроблені як референс) |
| **B — агент і Playwright** | Dev B | `agent/` | B1 … B7 |
| **C — документація, фікстури, ops** | Dev C | `docs/`, `fixtures/`, `README.md` | C1 … C8 |
| **D — інтеграція і захист** | усі разом | — | D1 … D4 |

Всередині треку тікети переважно послідовні (A3 → A4 → A5), між треками —
паралельні. Єдині справжні синхронізації: `A5 + B2 → B3` і `B4 → C4/C5`.

## Порядок і критичний шлях

```
день 1   A3            B1            C1, C7          ← старт паралельно
день 2   A4            B2            C6
день 3   A5            (чекає A5)    C3
день 4   A6, A7        B3            C2   ← контракти фіналізуються після A5
день 5   —             B4, B5, B6    C4
день 6   —             B7            C5, C8
день 7   D1, D2, D3, D4                          ← репетиція захисту
```

Критичний шлях: **A3 → A4 → A5 → B3 → B4 → D1 → D2**. Якщо трек A відстає,
трек B робить B1, B2, B5 (обробку збоїв), а трек C — усе, що не залежить від
фінальних схем.

## Що вже зроблено в скелеті

- MCP-сервер запускається окремим процесом, віддає 5 інструментів з явними
  input і output схемами (`python scripts/verify_mcp.py` це доводить);
- `ingest_timetable_snapshot` і `detect_timetable_changes` реалізовані повністю
  і слугують зразком стилю для решти;
- таксономія помилок, версіоновані снапшоти, детермінований демо-датасет,
  три записані фікстури (v1, змінена v2, зламана сторінка);
- каркас агента: конфіг, підключення обох MCP, граф із маршрутизацією,
  фасад із логуванням кожного MCP-виклику;
- GitHub-автоматика: тікети, мітки, мілстоуни, `/take`, авторозблокування
  залежностей, CI.

Решта — у тікетах.

## Розклад змінюється: як це враховано

Розклад університету редагують посеред семестру, тому «один раз спарсили і
готово» не працює. У моделі це вирішено так:

1. кожен збір сторінки створює **новий версіонований снапшот**; ідентичний
   вміст дає той самий `snapshot_id` і не дублюється;
2. план завжди привʼязаний до `snapshot_id`, з якого його побудували;
3. `detect_timetable_changes` порівнює свіжий снапшот із попереднім і окремо
   рахує, які пункти чинного плану зламалися (`removed` / `moved`);
4. `replan_required` вмикає повторну оптимізацію — і це саме той випадок, коли
   результат інструмента визначає наступний крок агента;
5. якщо змін немає, флоу коротким шляхом іде у звіт і не витрачає токени.

На захисті це показується перемиканням фікстури v1 → v2: один клас переїхав на
інший день, один додався, агент сам це помічає й переплановує.

## Можливі розширення (не робимо зараз, згадуємо на захисті)

- Obsidian MCP як другий existing-сервер: агент пише план відвідування і
  причини пропусків у нотатку-журнал.
- Дедлайни з експортованого `.ics` Moodle як додаткове мʼяке обмеження в
  оптимізаторі.
- Telegram saved messages — не проходить за вимогою «public API without
  authentication», тому лише як напрямок.
